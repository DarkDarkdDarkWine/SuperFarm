# 开发会话记录 2026-03-22

## 本次解决的问题

### 1. 回合顺序 Bug（最复杂）

**现象**：玩家1掷完骰子后，玩家2也立刻掷骰子，然后才一起结算繁殖——两个玩家的回合变成并行。

**根因**：服务端在人类回合结束后立即执行 AI 回合，AI 的 `game:dice_rolled` 事件在人类回合动画还未播完时就到达客户端。客户端的 `DICE_ROLLED` reducer 无差别清空了 `eventQueue`，导致当前回合未播完的事件丢失，两个回合的骰子叠加在同一时间线上。

**解法**：在客户端引入 `pendingTurns: TurnEntry[]` 队列。收到骰子事件时，如果当前不处于空闲的 `exchange` 阶段，就把它压入队列而非立刻播放。当前回合所有事件播放完毕（`popQueue`）后，再从队列中取出下一个回合开始播放。

**教训**：服务端推送速度 > 客户端消费速度时，必须在客户端加缓冲队列，不能假设事件总是按序消费完。

### 2. LLM 不工作（最隐蔽）

**现象**：AI 决策全部显示"规则兜底"，LLM 似乎从未被调用。

**排查过程**：
1. 怀疑是提示词问题 → 改了提示词 → 没用
2. 查后端日志 → `AI API error: Authorization Required` → API Key 为空
3. 追根溯源：`POST /api/config` 只更新后端内存，Docker 容器重启后内存清空，Key 丢失
4. 用户配置的 Key 存在 localStorage，但页面刷新后不会自动推给后端

**解法**：在 `SetupPage.tsx` 挂载时，从 localStorage 读取已保存的 Key/Provider/Model，自动 `POST /api/config` 恢复后端内存状态。

**教训**：内存状态 ≠ 持久化状态。当系统存在"内存 + 持久化"两层存储时，必须在适当时机做同步恢复，否则重启就是静默故障。

---

### 3. 狼规则错误

**现象**：狼攻击后兔子也被清零。

**根因**：`processWolfAttack` 里 `animalsLost` 数组包含了 `rabbit`。

**修复**：从数组中移除 `rabbit`，同步更新 `docs/game-rules.md` 和 `CLAUDE.md`。

**教训**：规则文档和实现代码要保持同步。规则变更时两边都改，以文档为权威。

---

### 4. AI 难度同质化

**现象**：三种难度的 AI 行为完全一样，提示词里大量"必须"指令让所有 AI 都激进执行。

**根因**：把"必须换羊""必须换猪"写死成强制指令，差异化靠风险偏好描述，但 LLM 对"风险偏好"的理解不如对"数值阈值"稳定。

**解法**：改用**决策精度**区分难度：
- easy：2倍阈值，每回合最多一步，有时什么都不做
- medium：标准阈值，偶尔连锁
- hard：穷举所有升级路径，连锁执行到底

**教训**：设计 AI 难度时，用可量化的行为差异（阈值、步数上限）比用抽象性格描述更有效。"必须"类指令会消除所有难度差异。

---

### 5. 购买防护 UI 错误

**现象**：点击"买大狗"没反应。

**根因**：`canBuySmallDog` 检查的是 `animals.rabbit`（应该是 `animals.sheep`），`canBuyBigDog` 检查的是 `animals.sheep`（应该是 `animals.cow`）。

**教训**：UI 的可用状态检查逻辑要和实际规则严格一致，否则按钮永远灰着。

## 有价值的工作方法

### 方法一：先看日志，再动代码

遇到"功能不工作"类 Bug 时，第一步永远是看运行时日志，而不是凭直觉猜测。

本次 LLM 不工作的排查：
1. 先以为是提示词问题（猜测）→ 改了没用
2. 查日志 → `Authorization Required` → 马上定位到 Key 为空
3. 追问"为什么 Key 为空" → 发现容器重启会清内存

**原则**：日志告诉你*发生了什么*，代码告诉你*为什么*。顺序不能反。

---

### 方法二：加调试日志要精准，用完要删

本次为了定位 LLM 问题，加了两行调试日志：
```
AI decision for 天才李四: LLM=true, actions=1, thinking=14449ms
[AI raw response] <think>...
```

这两行立刻暴露了问题：LLM 确实在返回响应，actions=0 是 AI 真的觉得没什么可换（早期 1-3 只兔子），而不是调用失败。

**原则**：调试日志要打印关键决策点的输入和输出（不是过程），能让你一眼看出"这条路走通了没"。用完即删，不污染生产日志。

---

### 方法三：区分"静默成功"和"真正工作"

`actions=0` 有两种含义：
- LLM 调用成功，AI 判断本回合无操作（正常）
- LLM 调用失败，error handler 返回空数组（故障）

原来的代码两种情况都走规则兜底，用户完全看不出区别。通过给日志加 `LLM=true/false` 字段，立刻能区分这两种情况。

**原则**：系统的"正常空结果"和"故障降级"要有可观测的区别，否则故障会长期静默。

---

### 方法四：状态持久化的三层模型

本次 Key 丢失问题揭示了一个常见的架构陷阱：

```
用户配置 → localStorage（持久） → 后端内存（易失）
```

任何依赖内存状态的后端功能，在服务重启后都会静默失效。解法是在合适的生命周期节点（页面挂载、登录、连接建立）做内存恢复，把持久层同步到内存层。

**原则**：设计配置系统时，明确每一层的生命周期，在层与层之间建立同步机制，而不是假设内存永远有效。

---

### 方法五：文档和代码同步修改

本次狼规则的修正，改了代码但文档没同步，导致下一次读文档时看到的还是旧规则。

**工作流程**：
1. 规则类变更：文档先行，代码跟随
2. 实现类变更：代码完成后，文档同步更新
3. 提交时：代码和文档在同一个 commit 里

**原则**：文档和代码是同等重要的制品，分开提交就是在制造技术债。

---

### 方法六：LLM 提示词设计——用数值约束代替性格描述

设计 AI 难度差异时，"稳重""激进"这类性格词没有量化约束，LLM 会根据自己的理解自由发挥，导致难度差异消失。

有效的方式是给出可量化的行为约束：
- "兔子积累到 12 只才换羊"（明确阈值）
- "每回合最多执行一步操作"（明确步数上限）
- "扫描所有升级路径，连锁执行到底"（明确策略算法）

**原则**：LLM 提示词里的行为约束越具体越好，量化 > 描述，边界条件 > 原则性陈述。
